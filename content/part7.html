Giving up order to keep one fact

An AVL tree maintains a total order, and pays for it with a rotation on almost every insert. A heap maintains almost nothing: only that the maximum sits at the root. That is all a priority queue needs, and giving up everything else makes the structure dramatically simpler — no pointers, no rotations, just an array.

The priority queue problem

A server runs jobs, each with an expected run time. The policy is shortest remaining processing time. You need: find the next job to run, delete a job when it finishes, and insert a job when it arrives. A sorted array gives \(O(1)\) find and \(O(n)\) insert; an unsorted array gives \(O(n)\) find and \(O(1)\) insert. A heap gives \(O(1)\) find and \(O(\log n)\) for both — the best of both, which is exactly the trade a heap is designed for.

The heap property and the array layout

Definition — max-heap

A complete binary tree in which every node's key is greater than or equal to the keys of its children. Completeness means every level is full except possibly the last, which fills from the left — and that is precisely what allows the tree to be stored in an array with no gaps.

For a node at index i (0-based): left child = 2i + 1 right child = 2i + 2 parent = floor((i - 1) / 2)
Worked example — reading a heap as an array

Array [10, 5, 3, 4, 1] represents:

Tree5 nodes, height 2
            10 (index 0)
           /            \
       5 (1)            3 (2)
      /     \
   4 (3)    1 (4)

Check the property: 10 ≥ 5 and 10 ≥ 3; 5 ≥ 4 and 5 ≥ 1. Valid max-heap. Node 3 at index 2 has children at indices 5 and 6, both beyond the array — it is a leaf.

The operations in pseudocode

Everything is written for a 0-indexed array, which is what the C and Python code below use. If a question uses 1-based indexing, the child formulas become 2i and 2i+1 and the parent becomes floor(i/2) — check which convention is in play before writing anything.

PseudocodeINDEX ARITHMETIC AND SIFTING
PARENT(i) = floor((i - 1) / 2)     # 0-indexed
LEFT(i)   = 2 * i + 1
RIGHT(i)  = 2 * i + 2

SIFT-DOWN(A, n, i):               # restore heap from a too-small root, O(log n)
    while true:
        l = LEFT(i);  r = RIGHT(i);  big = i
        if l < n and A[l] > A[big]: big = l
        if r < n and A[r] > A[big]: big = r
        if big == i: return        # parent already dominates both children
        swap A[i], A[big]
        i = big                    # follow the hole downward

SIFT-UP(A, i):                    # restore heap after appending at the end, O(log n)
    while i > 0:
        p = PARENT(i)
        if A[p] >= A[i]: return
        swap A[p], A[i]
        i = p                      # follow the hole upward
PseudocodePRIORITY QUEUE OPERATIONS
HEAP-MAXIMUM(A):                  # O(1)
    if A is empty: error "empty heap"
    return A[0]

HEAP-INSERT(A, x):                # O(log n)
    A.length = A.length + 1
    A[A.length - 1] = x
    SIFT-UP(A, A.length - 1)

HEAP-EXTRACT-MAX(A):              # O(log n)
    if A is empty: error "empty heap"
    max = A[0]
    A[0] = A[A.length - 1]         # move last leaf to the root
    A.length = A.length - 1
    if A.length > 0: SIFT-DOWN(A, A.length, 0)
    return max

BUILD-HEAP(A):                    # O(n), NOT O(n log n)
    for i = floor(A.length / 2) - 1 down to 0:
        SIFT-DOWN(A, A.length, i)  # start at the last internal node

HEAPSORT(A):                      # O(n log n) time, O(1) extra space
    BUILD-HEAP(A)
    for end = A.length - 1 down to 1:
        swap A[0], A[end]          # largest goes to its final position
        SIFT-DOWN(A, end, 0)       # heap is now the prefix A[0 .. end-1]
The one line that explains build-heap's cost

The loop starts at floor(n/2) - 1, not at 0 — that is the last node that actually has children. Every node after it is a leaf and needs no work. Combined with the fact that a node of height k costs only k to sift and there are very few tall nodes, the total is linear. Starting the loop at 0 instead would add n/2 wasted calls but would not change the asymptotics.

Worked trace — build-heap

The last internal node is at index \(\lfloor 5/2 \rfloor - 1 = 1\). Sift down from there back to index 0.

Why build-heap is O(n) and not O(n log n)

Sifting down from a node of height \(k\) costs \(O(k)\). A complete tree has at most \(\lceil n/2^{k+1}\rceil\) nodes of height \(k\). So the total is

\[ \sum_k k \cdot \frac{n}{2^{k+1}} = \frac{n}{2}\sum_k \frac{k}{2^k} = \frac{n}{2}\cdot 2 = O(n) \]

because \(\sum k/2^k\) converges to 2. Most nodes are near the bottom where subtrees are tiny, and that is what makes the sum linear.

Heap

Heapsort

Build a max-heap, then repeat \(n-1\) times: swap the root with the last element, shrink the heap by one, and sift the new root down. The largest element lands in its final position on each pass, and the sorted region grows from the right.

Cheap.c
#include <stdio.h>

static void swap(int *a, int *b) { int t = *a; *a = *b; *b = t; }

/* restore the heap property in the subtree rooted at i, heap size n */
static void sift_down(int a[], int n, int i) {
    while (1) {
        int l = 2 * i + 1, r = 2 * i + 2, big = i;
        if (l < n && a[l] > a[big]) big = l;
        if (r < n && a[r] > a[big]) big = r;
        if (big == i) break;
        swap(&a[i], &a[big]);
        i = big;
    }
}

/* O(n) */
void build_heap(int a[], int n) {
    for (int i = n / 2 - 1; i >= 0; i--)
        sift_down(a, n, i);
}

/* O(n log n) time, O(1) extra space */
void heapsort(int a[], int n) {
    build_heap(a, n);
    for (int end = n - 1; end > 0; end--) {
        swap(&a[0], &a[end]);   /* max goes to its final place */
        sift_down(a, end, 0);    /* restore over the shrunk heap */
    }
}

int main(void) {
    int a[] = {4, 10, 3, 5, 1};
    int n = 5;
    heapsort(a, n);
    for (int i = 0; i < n; i++) printf("%d ", a[i]);   /* 1 3 4 5 10 */
    printf("\n");
    return 0;
}
Pythonheap.py
def sift_down(a, n, i):
    while True:
        left, right, big = 2 * i + 1, 2 * i + 2, i
        if left < n and a[left] > a[big]:
            big = left
        if right < n and a[right] > a[big]:
            big = right
        if big == i:
            return
        a[i], a[big] = a[big], a[i]
        i = big


def build_heap(a):
    """O(n) - bottom-up."""
    for i in range(len(a) // 2 - 1, -1, -1):
        sift_down(a, len(a), i)


def heapsort(a):
    """O(n log n) time, O(1) extra space."""
    n = len(a)
    build_heap(a)
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]
        sift_down(a, end, 0)

Python's heapq is a min-heap

heapq gives the smallest element first. For a max-heap, either negate the values on the way in and out, or store tuples (-priority, item). This is a favourite exam question.

Common mistakes

  1. Using the wrong child formula. Zero-based: children are \(2i+1\) and \(2i+2\). One-based (as in some textbooks): \(2i\) and \(2i+1\). Check which the question uses.
  2. Claiming build-heap is \(O(n\log n)\). It is \(O(n)\); the summation above is the proof.
  3. Forgetting that a heap is not sorted. The array [10, 5, 3, 4, 1] is a valid heap but not sorted, and inorder traversal of a heap is meaningless.
  4. Assuming heapsort is stable. It is not — the swap at the root destroys relative order of equal keys.
  5. Sifting the wrong direction. Insert sifts up; delete-max and build-heap sift down.

Check your understanding

Is [9, 7, 8, 3, 5, 2] a valid max-heap?
Check the parent-child pairs: 9 ≥ 7 and 9 ≥ 8; 7 ≥ 3 and 7 ≥ 5; 8 ≥ 2. All hold, so it is a valid max-heap. A heap need not be sorted — 7 and 8 are siblings, and there is no ordering requirement between siblings.
What is the time complexity of build-heap on n elements?
The naive count overestimates because it assumes every sift-down costs log n. In fact a node of height k costs only k, and there are very few tall nodes. Summing k·n/2^(k+1) over k gives 2n, so the bound is O(n).
